# Agent Runtime: decoupling and controller co-location

Analysis for [#7](https://github.com/urucoder/local-studio/issues/7), under [#3](https://github.com/urucoder/local-studio/issues/3). Inspected source baseline: `0978c4a7329da9e70adb179aca14eb5e91411d2d`, on 2026-09-07. No implementation is included. Source links below are repository-relative, with line ranges at that baseline; proposed behavior is explicitly labeled.

This builds on [PR #6's refactor options](https://github.com/urucoder/local-studio/blob/6f2820ea2102a1459c267eb5a3be3e6889309848/docs/architecture/refactor-options.md), especially Phase 1 and the investigative portion of Phase 3, rather than repeating the general architecture guide. That document is not present in this checkout; the linked PR version was read separately.

## Executive findings

- **A non-Electron entrypoint exists, but a supported independent service profile does not yet follow from it.** The runtime binds loopback, starts background scheduling, and exits immediately on signals; Electron ordinarily owns its child and its OAuth vault. See [boot](../../services/agent-runtime/src/server.ts#L1-L23) and [desktop launch](../../frontend/desktop/logic/agent-runtime-server.ts#L83-L165).
- **The issue's bypass inventory is partly historical.** Connectors, plugins, projects, skills, and prompt templates already have proxied routes and runtime handlers. Four frontend modules still import stateful runtime services; filesystem/git/terminal and desktop IPC introduce additional wrong-host behavior. See the complete consumption inventory below and [runtime routing](../../services/agent-runtime/src/http/app.ts#L166-L197).
- **Co-location needs configuration, not a new model transport.** The runtime uses HTTP to discover models and configures Pi with controller `/v1` URLs and credentials; it does not require controller source in-process. Persisted secondary-controller URLs must migrate too. See [`mergeControllers` and model configuration](../../services/agent-runtime/src/pi-runtime-models.ts#L219-L287), [discovery](../../services/agent-runtime/src/pi-runtime-models.ts#L318-L375), and [Pi configuration](../../services/agent-runtime/src/pi-runtime-models.ts#L412-L506).
- **Do not assume the raw runtime hosts KittyLitter's gateway.** Its route registry has no pairing/gateway service; the frontend pairing route calls a separate `kittylitter pair` executable. The gateway/relay implementation is outside this inspected path. Keeping this Node process alive is necessary for runtime availability, but does not prove phone pairing or “Mac off” works. See [runtime app](../../services/agent-runtime/src/http/app.ts#L125-L243), [pairing route](../../frontend/src/app/api/kittylitter/pairing/route.ts#L1-L19), and [CLI invocation](../../frontend/desktop/logic/kittylitter-pairing.ts#L64-L92).
- **Recommendation:** retain the prior recommendation: Option C's private network topology with Option A's single runtime/state owner. Start with separately supervised controller/runtime services on one VM and an authenticated front door. Containers are a viable next packaging profile, not a substitute for authorization, OAuth redesign, or state migration.

## 1. Process, entrypoints, and lifetime

### Boot and packaging

[`server.ts:6–23`](../../services/agent-runtime/src/server.ts#L6-L23) calls `startAutomationScheduler()`, constructs the Hono app and session-list watcher, then serves it:

```ts
const port = Number(process.env.PORT) > 0 ? Number(process.env.PORT) : 8081;
serve({ fetch: app.fetch, port, hostname: "127.0.0.1" }, ...);
```

There is no host environment override here, and positive-but-invalid ports are not rejected by a boundary schema before reaching the server library. The watcher starts only after listen; it watches project/session roots, debounces notifications by 200 ms, refreshes roots every 15 seconds, and tolerates watcher failures. Scheduling starts before listen, ticks immediately and every 30 seconds, and can start model-backed turns without a connected UI. Sources: [watcher](../../services/agent-runtime/src/session-list-watcher.ts#L6-L110), [scheduler tick/start](../../services/agent-runtime/src/automation-scheduler.ts#L210-L239), [automation execution](../../services/agent-runtime/src/automation-scheduler.ts#L150-L207).

There are three distinct artifacts/modes, not one Electron binary:

Consequences:

- `DESKTOP_CONFIG.userDataDir` is `app.getPath("userData")`, not an intrinsic runtime requirement ([configs.ts:6–13](../../frontend/desktop/configs.ts#L6-L13)). Without Electron injection, runtime data defaults to `~/.local-studio`; resolution creates the directory, attempts mode 0700, and may copy legacy `api-settings.json` on first resolution ([data-dir.ts:28–109](../../services/agent-runtime/src/data-dir.ts#L28-L109)). Use an explicit absolute service directory and deliberate initial settings to avoid service-home-dependent migration.
- An externally set `LOCAL_STUDIO_AGENT_RUNTIME_URL` **does not select a remote runtime for Electron**: startup chooses a local handle and overwrites the value in Next's environment. By contrast the production frontend launcher honors a healthy remote URL. The actual remote socket must be reachable and compatible with the runtime Host check; an arbitrary remote hostname cannot address today's raw loopback listener.
- `PORT` defaults to 8081 in raw runtime boot; `HOSTNAME` and controller's `LOCAL_STUDIO_HOST` do not change its fixed bind. Electron may allocate an ephemeral runtime port; `resolveStablePort` falls back to OS allocation ([ports.ts:20–48](../../frontend/desktop/helpers/ports.ts#L20-L48)).
- `BACKEND_URL` and `API_KEY` are inherited, not manufactured by either runtime launcher. Saved settings take precedence over defaults. Backend default precedence is `BACKEND_URL`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_BACKEND_URL`, then `http://localhost:8080`; key default is `API_KEY` or empty. A remote backend means outbound HTTP from the **runtime host**, not the desktop. [backend-url.ts:18–23](../../shared/agent/backend-url.ts#L18-L23), [settings-service.ts:17–34](../../services/agent-runtime/src/settings-service.ts#L17-L34).
- `LOCAL_STUDIO_FRONTEND_BASE` is a functional dependency: bundled connector/CUA/subagent/automation tools call it. With no value, runtime helpers derive `http://127.0.0.1:${PORT || "3000"}`; if `PORT` is also absent this differs from runtime's 8081 default. A URL pointing at the Mac retains a Mac-availability dependency. These tools' `/api/agent/*` destinations already exist in the runtime, so a future service profile can deliberately target its private API instead, with service authentication. Sources: [helper:155–158, 298–334](../../services/agent-runtime/src/pi-runtime-helpers.ts#L298-L334), [connectors:19–111](../../frontend/desktop/resources/pi-extensions/connectors.ts#L19-L111), [CUA:38–68](../../frontend/desktop/resources/pi-extensions/cua.ts#L38-L68), [subagents:21–157](../../frontend/desktop/resources/pi-extensions/subagents.ts#L21-L157), [automations:22–216](../../frontend/desktop/resources/pi-extensions/automations.ts#L22-L216).

### Complete `proxyToAgentRuntime` route inventory

[`proxy-to-runtime.ts:3–63`](../../frontend/src/app/api/agent/proxy-to-runtime.ts#L3-L63) uses `LOCAL_STUDIO_AGENT_RUNTIME_URL` or `http://127.0.0.1:8081`, preserving pathname/query/method. It copies request headers then removes `host`, `connection`, `content-length`, and `accept-encoding`; **authorization/cookie headers are not stripped**, and no dedicated service credential is injected. Request bodies are buffered (with per-route optional bounds), while the response body is streamed through and request cancellation is forwarded. Connection failure returns 502. A front door needs an explicit credential-forwarding policy, stream-compatible timeouts, and client/service auth separation.

## 3. State and identity ownership

### Classification rules and completeness boundary

**Move-with-runtime** means one authoritative writable copy on the service host, with an offline rollback backup if needed. **Stay-with-desktop** means device-specific state, not mounted into the service. **Can-duplicate** means immutable content or regenerable cache, not two writers to credentials/sessions/schedules. ### State outside this root that a migration must not miss

- **Native Pi home:** provider auth defaults to `~/.pi/agent/auth.json` without `PI_CODING_AGENT_DIR`; custom model input uses that directory or the override; plugin discovery writes `<Pi agent dir>/extensions` (including disabled `.off` files). `PI_CODING_AGENT_SESSION_DIR` or Pi settings can move sessions elsewhere. **Move-with-runtime** the intended credentials/session/settings/extension set, not every unrelated local agent's home. [Provider paths](../../services/agent-runtime/src/provider-hub.ts#L111-L125), [model input](../../services/agent-runtime/src/pi-runtime-models.ts#L20-L25), [plugins](../../services/agent-runtime/src/user-plugins.ts#L10-L49), [sessions](../../services/agent-runtime/src/sessions-store.ts#L72-L103).
- **Workspaces and chat workspace:** project JSON records paths, not project contents. The shared project store also creates a built-in chat project at `~/.local-studio` ([projects-store-core.ts:115–140](../../frontend/desktop/logic/projects-store-core.ts#L115-L140)), even when the data root is overridden. **Move-with-runtime** the remote workspace contents and registrations; **stay-with-desktop** intentionally local workspaces. Do not mount the entire Mac home as a shortcut.
- **Skills/prompts/resources:** discovery reads `.pi`, `.claude`, `.codex`, `.factory`, `.opencode`, and macOS Codex application resource locations ([skill-discovery.ts:20–58](../../services/agent-runtime/src/skill-discovery.ts#L20-L58)); prompt sources include `.pi`, `.claude`, `.codex` ([prompt-templates-store.ts:21–30](../../services/agent-runtime/src/prompt-templates-store.ts#L21-L30)). **Can-duplicate** selected immutable content subject to its distribution rights; resource paths and installed applications are not portable automatically.
- **Browser sessions:** current Playwright contexts are ephemeral, with no user-data directory ([playwright.ts:12–27, 60–79](../../services/agent-runtime/src/browser-host/playwright.ts#L60-L79)). There is no persistent runtime browser-cookie directory to migrate from this code path.
- **Controller database/config/models:** **stay with the controller** (on the proposed co-located host), not desktop state and not runtime-store replicas. `LOCAL_STUDIO_DB_PATH`, controller data/model paths and persisted settings are independent ([controller env:137–189](../../controller/src/config/env.ts#L137-L189)).

### Stable identity: correction and proposed invariant

Current runtime boot and health expose a PID, not a stable gateway identity; the pairing helper validates external `{v, node_id, token, host_name?, relay?}` JSON. There is no basis here to equate `node_id`, controller API key, a frontend historical `controllerId`, or a gateway secret. [Runtime boot](../../services/agent-runtime/src/server.ts#L6-L23), [health](../../services/agent-runtime/src/http/app.ts#L135-L137), [pairing JSON](../../frontend/desktop/logic/kittylitter-pairing.ts#L34-L58).

**Proposed:** give the authoritative runtime/gateway a persistent identity and rotatable credentials in service-owned durable storage, separate from Electron's userData and separate from controller access credentials. Import an existing gateway identity only after the external protocol confirms its format/ownership; otherwise pair anew. A fixed absolute data path already preserves the runtime's ordinary stores across Node restarts, but does not itself implement a gateway identity protocol.

Existing atomic renames and process-local serialization are not a distributed multi-writer design. For example [session-json-store.ts:5–17](../../services/agent-runtime/src/session-json-store.ts#L5-L17) uses an in-process promise chain and [oauth-connectors.ts:122–139](../../services/agent-runtime/src/oauth-connectors.ts#L122-L139) serializes within one process. Migration should stop the source, snapshot, remap/reencrypt, validate cold startup, then enable exactly one scheduler/writer. The [dev-channel mirror](../../frontend/desktop/logic/dev-channel-mirror.ts#L13-L32) is not a remote replication or comprehensive secret migration mechanism.

## 4. Controller co-location: confirmed behavior

`refreshPiModels` reads runtime-host API settings and `<dataDir>/pi-agent/controllers.json`. Nonempty controllers from a request take precedence over that persisted list; otherwise the saved list is reused. `mergeControllers` uses the primary settings controller only when the requested/saved list is empty. For a listed primary without a key, it backfills the saved primary key when normalized identities match (`localhost`, `127.0.0.1`, and `[::1]` are equivalent at the same scheme/port/path). Final list deduplication uses normalized URL strings, not that broader identity. [pi-runtime-models.ts:185–287](../../services/agent-runtime/src/pi-runtime-models.ts#L185-L287), [467–480](../../services/agent-runtime/src/pi-runtime-models.ts#L467-L480).

Discovery calls `<controller.url>/v1/models` with bearer authorization when a key exists, a 2.5 s timeout, and a 60 s in-memory negative cache for connection failures. Controllers are queried concurrently; successful results survive failures of others. A generated `pi-agent/models.json` configures Pi's `openai-completions` provider at `<controller.url>/v1`, with auth enabled only for configured keys; custom Pi providers and provider-hub models are also merged. [Discovery/cache:290–409](../../services/agent-runtime/src/pi-runtime-models.ts#L290-L409), [provider configuration:412–506](../../services/agent-runtime/src/pi-runtime-models.ts#L412-L506). Title generation separately uses the **primary** saved backend's `/v1/chat/completions`, not the full merged-controller selection ([title-handlers.ts:38–65](../../services/agent-runtime/src/http/title-handlers.ts#L38-L65)).

**Same VM/network namespace:** configure runtime primary backend as `http://127.0.0.1:8080` and set/migrate its API key to match controller's `LOCAL_STUDIO_API_KEY`. Controller defaults to `LOCAL_STUDIO_HOST=127.0.0.1`, `LOCAL_STUDIO_PORT=8080`; inference defaults separately to localhost:8000. It accepts bearer authorization or `X-API-Key` and uses timing-safe comparison. Co-location does not remove HTTP or automatically share credentials, data, or authentication middleware. [Controller config:112–174](../../controller/src/config/env.ts#L112-L174), [auth:65–123](../../controller/src/http/security-middleware.ts#L65-L123).

**Separate containers:** `localhost` means each container itself, not its neighbor. A private controller service DNS URL can be used without changing runtime model transport, but controller bind/auth must permit it. Today's runtime loopback bind/Host guard prevents ordinary bridge-network access from a separate gateway container. Either explicitly share a private network namespace for an initial topology or implement authenticated configurable private listening; do not publish the raw runtime port.

**Migration traps and expected improvements (derived from the cited code):**

- Changing `BACKEND_URL` alone will not override a nonempty saved `backendUrl`; changing primary settings alone will not discard nonempty `controllers.json`. Reconcile both and regenerate model config.
- Desktop-origin `localhost` controller/project choices change meaning on the service host. Stable controller IDs in a future contract should resolve server-side, rather than treating arbitrary client-supplied URLs as authoritative.
- Shorter controller RTT and independence from the Mac should improve availability, but inference capacity/loading is still controller-owned; co-location is not a latency or GPU-capacity guarantee.
- Keep controller and runtime data directories **separate**, even if both use the same environment variable name. Controller's data root owns `controller.db` and persisted config; the runtime owns different files. There is no shared-database coupling in model discovery. [Controller data/config:137–189](../../controller/src/config/env.ts#L137-L189).
- Frontend `/api/proxy/*` remains a separate controller access path until the bypass work is complete; placing only the runtime beside the controller does not relocate desktop-local route handlers.

## 6. Deployment options and recommendation

These are **proposals**, not existing deployment manifests or measured estimates. S/M/L denotes relative work: S = packaging/configuration once shared prerequisites exist; M = a service-lifecycle or platform integration workstream; L = cross-boundary state/client migration. All options need the same versioned contract, authorization, headless secrets, path ownership, and frontend bypass work identified above; packaging is not the dominant risk.

| Option | Configuration and topology | Desktop change | Relative sizing / principal risk |
| --- | --- | --- | --- |
| **A. Two systemd services on one Linux VM, private front door — recommended first** | Separate runtime and controller service users/data directories; fixed loopback runtime:8081 and controller:8080; separately supervised processes; staged Node bundle/resources plus Bun controller; private API credentials, OAuth backend, workspaces, PATH, logs/backups. Only authenticated TLS/VPN ingress is reachable by clients. | Add explicit local/remote profile; in remote mode do not fork/kill runtime or silently fall back locally. Pass the front-door URL and client identity to Next; close stateful and IPC bypasses. | Packaging S–M, shared refactor L. Fewest new network-namespace assumptions; host tools/Chrome require least privilege. GPU/inference resources remain a controller-host sizing concern. |
| **B. Compose stack: controller, runtime, gateway** | Separate images/volumes and secrets; private controller DNS, runtime bind/Host configuration and service auth; only gateway port published. Stage architecture-matched native modules/browser dependencies. Alternative transitional profile: shared private network namespace preserves loopback, with independently supervised containers. | Same remote profile and client/API migration as A; no desktop-specific data mounts into the service. | Packaging M, shared refactor L. Stronger reproducibility; more native browser/PTY/GPU and volume-permission work. Ordinary separate containers do **not** work just by changing the runtime URL today. |
| **C. One service container containing both processes plus private ingress** | One network namespace permits loopback unchanged; an actual multi-process supervisor must manage restart/shutdown and health of both processes, with separate data/secrets/workspaces. Not the existing `npm start` lifecycle-coupled Next launcher. | Same remote mode. Desktop and optional hosted Next are clients, never owners of container lifetime. | Packaging M, shared refactor L. Simplifies initial networking but couples upgrades, failure domains, and privilege boundaries; less attractive for independent runtime/controller releases. |

Recommend **A first, B as the reproducible deployment target if container operations are already preferred**. Keep one authoritative runtime for sessions/projects/connectors/schedules and expose only an intentional, authenticated, versioned API through the front door. Preserve local-only mode as another launch profile, not a second continuously writing replica. This is exactly [the prior Option C + Option A recommendation](https://github.com/urucoder/local-studio/blob/6f2820ea2102a1459c267eb5a3be3e6889309848/docs/architecture/refactor-options.md#recommendation); it does not adopt the dual-owner synchronization design. A separately authenticated desktop worker is a later capability option only if Mac-local filesystem/browser/CLI parity is required.

No defensible numeric RAM/CPU sizing is available from these source paths. Size runtime for concurrent Pi sessions, PTYs, connector subprocesses, browser sessions, and retained transcripts; size inference/GPU capacity separately for controller-managed engines. Benchmark representative concurrency before offering VM sizes or availability guarantees.

## Open questions

1. Where is the authoritative KittyLitter gateway/relay/mobile implementation, and how does its node/token identity relate to the frontend's `controllerId`/gateway secret? The local CLI call and payload validator are not that protocol implementation.
2. Must remote sessions retain Mac-local filesystem, reveal/open, browser tabs, Obsidian, and local-agent configuration, or are those explicitly host-scoped features?
3. Is the first deployment Linux VM, container stack, or another always-on OS? What are the browser/display/native-binary and GPU requirements for that host?
4. Which headless secret store/key source and OAuth callback strategy are acceptable? Which provider callbacks support remote redirect URIs or manual/device-code alternatives?
5. What are the gateway contract, device scopes, revocation, token rotation, and API-version compatibility requirements? A private network alone does not answer authorization.
6. What is the migration/rollback policy for absolute project paths, historical session IDs/metadata, credentials, active schedules, and external relay identity? Do not enable both schedulers against copied state.
7. Which optional capabilities make readiness degraded versus failed, and what shutdown/reconnect guarantees should active turns and streams provide?

## Proposed follow-up implementation sub-issues

1. **Protocol and ownership contract:** obtain gateway/CLI/mobile source/spec; define runtime versus device/controller identity, versioned Effect Schema contracts, host-scoped workspace IDs, trust boundaries, and authorization. Exit: a reviewed endpoint/identity matrix, including pairing.
2. **Headless runtime foundation:** validated configuration, private authenticated listener, independent artifact/resources, supervisor packaging, capability readiness, scheduler/stream/child-process graceful shutdown, redacted logs. Exit: runtime remains healthy and can complete background work with Electron absent.
3. **State/identity migration:** authoritative runtime stores and settings API, reconcile controller lists, project/session path migration, re-encrypted headless OAuth secrets, gateway identity strategy, backup/import/rollback with single-writer cutover. Exit: cold restart preserves intended identity/history without duplicate automations.
4. **Close frontend and desktop bypasses:** settings/controller forwarding, filesystem/git/terminal host alignment, local-agent policy, explicit remote lifecycle profile and project IPC selection. Exit: audited remote actions never read/write desktop runtime stores or spawn a fallback runtime.
5. **OAuth and host-local capabilities:** callback brokerage/device flows where supported, browser/Chrome/Obsidian/CLI capability decisions, optional authenticated desktop worker. Exit: connecting from another machine reaches the correct host and secret owner.
6. **Gateway pairing and operational acceptance:** implement against the confirmed external protocol, short-lived bootstrap/device revocation, upgrade compatibility, backup/restore, reconnect/outage behavior. Exit: paired mobile and remote desktop work after Mac shutdown; local-only mode still works. Validate these behaviors in follow-up implementation work, not by adding tests in this analysis issue.

## Issue-summary comment

Ready-to-post summary for #7:

> The runtime has a Node/Bun entrypoint but remains lifecycle-coupled to Electron (or the production Next launcher when it owns the child). Setting a remote runtime URL alone is insufficient for the packaged desktop. In this checkout, connectors/plugins/projects/skills already use HTTP; the remaining stateful imports are settings, controller proxy resolution, local-agent setup, and filesystem workspace authorization, with additional desktop IPC/host-local behavior. Controller co-location already works over HTTP when saved primary and secondary-controller configuration is migrated. OAuth still depends on Electron's encrypted IPC vault and host-local callbacks. KittyLitter pairing invokes an external CLI; this source does not establish that the raw runtime hosts its gateway.
>
> Recommend separately supervised controller/runtime services on one always-on VM behind an authenticated front door, with one runtime/state owner; Compose is the next packaging alternative. Follow-ups: (1) protocol/ownership/security contract, (2) headless lifecycle/artifact, (3) state/identity/secret migration, (4) frontend and desktop bypass closure, (5) OAuth/host-local capabilities, (6) gateway pairing and Mac-off operational acceptance.
